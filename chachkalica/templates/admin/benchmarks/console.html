Overview

Five detection architectures × every registered variant × three export formats (.pt, .onnx, .engine), timed on synthetic random-init inputs in the trainer container — a compute-cost and precision-behavior instrument, not an accuracy measurement.

Measured on an otherwise-idle GPU so throughput is uncontended. Each format runs on GPU and attempts fp16 where safe, falling back to fp32 honestly wherever a format's own fp16 path isn't available (hover a FP32 badge for why). GPU utilization is an exact, per-process CUPTI reading for all three formats — a single value (mean == peak), not a whole-device NVML sample. Use the size switcher above to compare image sizes.

Reading the tables

One row per metric, three columns per variant (PT / ONNX / ENGINE), so a variant's cost across export formats reads left to right.

Precision
What actually ran. An fp16 request can fall back to fp32 per cell: ENGINE if TensorRT won't compile fp16 at that profile; PT if the adapter is supports_amp=False; ONNX if its fp16-cast graph won't load. A dotted-underline FP32 badge has the reason on hover.
Latency / Throughput
Per-image time (1000/fps) and images/sec over a timed predict() loop grown to ≥2 s, cuda.synchronize()-bracketed, with 5 untimed warmup calls first.
GPU Δmem
PT: exact max_memory_allocated(). ENGINE/ONNX: load-time before/after per-pid delta after a priming pass. ONNX's figure is arena reservation, not working set — compare it only to other ONNX cells.
GPU util
Exact, per-process, via CUPTI (torch.profiler, separate pass) — real kernel-busy % of wall clock, captured for onnxruntime and TensorRT kernels too. One true reading, so a single value is shown. The source is recorded per cell (gpu_util_method); runtime-native profilers and NVML remain as fallbacks.

Known limitations & explained anomalies

Odd-looking numbers in the tables above that are real and understood — none require a re-run. Grouped by cause.

  • DETR exported formats crater at large token grids. Both rfdetr and rtdetr (set-prediction decoders) lose most of their ONNX/ENGINE throughput at high resolution while PT stays fine — the attention/decoder ops export to launch-bound kernels that leave the GPU ~10–25% busy. At 960 rtdetr's engine even drops below its own PT (e.g. r50vd ~50 vs ~79 fps). PT eager fuses these, so PT is the fast path for a DETR at large input sizes.
  • rfdetr base is the worst case, at every size. base is the only variant with num_windows=4/patch_size=14 windowed attention (the rest are num_windows=2/patch_16); its 16-way window partition exports to a swarm of tiny kernels, so its ONNX/ENGINE degrade steadily (engine ≈ 212 → 62 → 18 fps at 320/640/960, util down to 10%) while PT holds ~85–116 fps. Prefer PT for base, or avoid base.
  • rfdetr large craters only at 704 (the 640 tab), not at 320/960. large is architecturally identical to medium; its slow 640-tab engine (~57 fps) is a resolution-specific TensorRT tactic cliff at the 44-patch grid (704 = 44×16, an awkward tile factor), not a size trend — it is ~536 fps at 320 and recovers to ~121 at 960. So the slowdown is base's windowing plus specific bad resolutions, not simply ">640".
  • PT throughput is overhead-bound at small sizes and doesn't track the page's image size for fasterrcnn/retinanet/rtdetr. Those three resize every input to a fixed internal size in their PT path, so their PT fps is ~flat across the 320/640/960 tabs (only ONNX/ENGINE, exported at the page size, actually scale). And at 320 the small/fast models finish faster than the host can feed them (yolox-nano PT ~14% util), so PT there reflects Python/launch overhead, not compute. Compare PT-to-PT across archs, not PT-to-engine within one size.
  • ONNX (fp32) often out-runs PT (fp16) on the small/fast nets (yolox, mobilenet_v3_large_320, the DETRs at 320). That is the same overhead effect plus onnxruntime's graph fusion — not a precision advantage; the PT number carries eager dispatch overhead.
  • fp16 → fp32 fallbacks, by design (hover an amber FP32 badge): fasterrcnn/retinanet/yolox ONNX (the shared fp16-cast graph is accepted by TensorRT but rejected by onnxruntime's session loader → fp32-on-GPU), and rtdetr PT (its adapter sets supports_amp=False for a documented decoder/GIoU fp16 overflow).
  • ONNX Δmem is arena reservation, not working set — onnxruntime grabs a pool on first Run() and reuses it, so ONNX reads high and flat (~526 MB floor at ≤640, up to 2–4 GB for the DETRs at 960 as feature maps grow). Compare ONNX-to-ONNX only.
  • ENGINE Δmem is coarse for the smallest models — per-pid NVML memory is attributed in blocks, so e.g. rfdetr's shared ViT-S encoder makes several variants read the same ~90 MB at 640. Where footprints genuinely diverge (yolox, rtdetr, fasterrcnn backbones) they scale as expected.
  • Variant order is not speed order within an arch — lighter backbones win, so listing order can look "inverted" (fasterrcnn mobilenet > resnet; yolox nano ≈ tiny). Expected.
  • Random-init weights throughout — no checkpoint, no real images. Says nothing about accuracy.
